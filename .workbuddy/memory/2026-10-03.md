## 缺陷修复：搜索弹窗「输入无反应 + 按钮关不掉」（用户实测发现）
- 根因：**变量暂时性死区（TDZ）**。`openSearchModal` 写成 `const root = openModal({ footer(){ ... root.querySelector(...) } })`，而 `openModal` 是**同步**执行 footer 回调的，此刻 `const root` 尚未赋值 → 抛 `ReferenceError`。
- 危害链：`openModal` 在 footer 那一步崩掉，导致其后的 `[data-close]` 按钮绑定、遮罩绑定、`#modal-x` 绑定**全部未执行**；`openSearchModal` 也整体中断，输入框监听未绑 → 弹窗渲染在页面上但完全僵死（输入无反应、按钮/ESC 都无效）。
- 修复 1：`openSearchModal` 的 keydown 绑定从 footer 回调内移到 `openModal` 返回之后。
- 修复 2（防御性）：`openModal` 改用**事件委托**在 `#modal-root` 上统一处理 `[data-close]` 关闭（不再逐按钮绑定），并把 body/footer 渲染回调包进 try/catch —— 任何页面回调抛错都只显示「界面渲染出错」而**不会产生关不掉的僵尸弹窗**；focus 前加 `document.contains` 守卫。
- 排查结论：TDZ 仅此一处。其余模态（`openAnimeForm` / `promptReview` / `openQuoteForm` / `openImportDialog`）虽也在 footer 里用 `root`，但都在**点击回调内部**（延迟执行，`root` 已赋值），安全。
- 回归：`tools/smoke.js` 增至 **61 项**，新增搜索弹窗可输入/可搜索/×关闭/「关闭」按钮/ESC 关闭，以及「回调抛错仍可关闭」用例。
- **教训（重要）**：`vm.Script` 语法校验和 49 项冒烟都曾全绿，却漏掉这个致命交互缺陷 —— 根因是**冒烟只调用了函数、没模拟真实用户输入与点击**。涉及 UI 交互的函数必须补「填值 + 派发 input 事件 + 真实点击 DOM 节点 + 断言弹窗可关闭」的用例。

## 封面墙改为 3D 翻转卡（用户提供 Uiverse 样式）
- 结构改为 `.card(perspective)` > `.card-3d(preserve-3d)` > `.fc-front`/`.fc-back`（两面 absolute + `backface-visibility:hidden`，hover 时 `.card-3d` 旋转 `rotateY(180deg)`）。

## 重看转盘「用不了」排查（用户报告）
用户报「转盘用不了」。**92 项冒烟全绿但从未抓到此问题** —— 测试只调 `spinWheel` 的数学分支，从未真实点过「开始」按钮，也从未构造「候选为 0」的数据状态。查出 2 个真实缺陷：

1. **候选为 0 时是死界面，且筛选里没有「全部作品」选项**（主因）
   - `wheelCandidates` 默认筛选 `all` = `st_done || st_watching || watchedEpisodes>0`。新入库作品默认 `st_want + 0 集` → **天然被排除**。用户若所有作品都没动过，候选恒为 0。

   - 筛选下拉原本只有「看过/在看、仅看过、仅神作」，**没有「全部作品」** → 用户根本没法把「想看」的作品放进转盘。
   - 修法：新增 `wheelEmptyDiagnosis()` 返回 `{reason, hint, actions}`，区分「片库为空 / 没有看过或在看 / 年代无作品 / 年代里没有符合筛选的 / 没标神作」五种原因；`renderWheel` 在候选为 0 时渲染 `#wheel-why` 诊断面板，引导按钮（`set-all`/`set-default`/`decade-clear`/`go-add`）**真的改 wheelState 再 rerender**。筛选新增 `value="any"` = 全部作品。

## 修复：自定义背景图「上传了却看不见」（21:00 后）

用户反馈上传背景图后界面毫无变化。排查出**五个缺陷叠加**，主因是一个条件写反。

### 根因

1. **深色主题硬编码禁用背景图**（主因）
   `applyAppearance()` 里 `useBg = settings.bg_image && settings.theme !== "dark"`，
   而 `DEFAULT_SETTINGS.theme` 恰好是 `"dark"`。于是默认状态下背景图**永远不可见** ——
   上传成功、toast 提示成功、界面毫无变化。设置页文案还写着「深色主题不支持自定义背景图」，
   把一个 bug 包装成了「设计如此」。

2. **`url('')` 静默失效**
   asset 读不到时 `bgImageUrl` 是空串，仍写出 `url('')`。这是非法值，
   浏览器静默当无背景 —— 失败表现得和成功一模一样。

3. **localStorage 必然溢出**
   实测降级模式下 4MB 可写、5MB 即 `QuotaExceededError`。手机照片 dataURL 普遍 3-5MB，
   原图几乎必然写不进去，用户只得到一句「存储空间不足」。

4. **导入路径 key 不一致**
   `applyImport` 把 `payloadBg` 存进新的 `bg_<时间戳>`，却让 `settings.bg_image`
   继续指着备份里的旧 key —— 该 key 在本机不存在，导入后背景图必然失效。

5. **浅色主题遮罩取深色**
   三个主题一律 `rgba(6,10,16,*)`，浅色主题下把背景压成脏灰。

### 修复

- 三主题统一支持背景图，可读性交给遮罩与模糊控制。
- 新增 `bgRenderable()` / `bgLostReason()`，无图显式写 `none`。
- 新增 `compressBgImage()`：canvas 缩到长边 1920 + JPEG 0.82，入库前压缩。
  GIF/SVG 跳过（丢动画 / 本身够小）；压缩失败退回原图，交给后续错误提示接住。
- 上传后**回读校验**，失败即把状态摆平，不留「设置里有图、实际读不出」的僵尸态。
- 导入时同步迁移 key；失败则清空 key 并记入 warnings。
- 遮罩色跟随主题（`--bg-overlay-rgb`），上限提到 0.92。
- 设置页新增缩略图预览 + 状态行（三态：有图生效 / 数据丢失 / 未上传）。

### 附带发现：可读性硬伤

新写 `tools/bg-contrast.js` 实测后发现：深色主题 + 纯白背景图时，
页头/间隙等**裸露区**（无面板遮挡）的正文对比度只有 **2.48:1**，完全读不清。
面板区因为 `.panel` 不透明反而没事 —— 这正是漏测的地方。

解决：`bgEffectiveOverlay()` 取「用户设定值」与「可读性下限」的**较大者**。
按纯黑/纯白两端夹逼估算下限（背景图亮度未知，纯色海报恰是最易崩的输入）。
最差值从 2.48:1 提到 **4.97:1**，三主题全部达到 WCAG AA。
代价：极端亮图会被压暗，但好过看不清正文。

### 方法论教训（第四次同类，且最隐蔽的一次）

前三次都是「断言只覆盖正常路径」。这次更特殊：**断言全绿、语法全绿，
功能却 100% 不可用**。原因是没有任何一条断言检查「深色主题下背景图是否可见」——
因为默认主题就是深色，而所有人都默认「背景图功能能用」。

固化两条新通则：
1. **「支持范围」类条件必须逐值枚举测试。** `theme !== "dark"` 这种条件，
   只要默认值落在被排除的那一侧，整个功能就是死的。要写
   `for (const theme of [...THEMES])` 的循环断言，而不是测一个「代表值」。
2. **失败态必须与成功态可区分。** `url('')` 和 `url(真实值)` 在页面上可能长得一样。
   凡是有「静默降级」的分支，都要断言它写出的值与成功路径**不同**。
